# Feature-Sliced Design

> **Архитектурная методология для frontend-проектов.** Делит код по слоям (что это: страница / виджет / фича / сущность / переиспользуемое) и навязывает правила импортов между ними. Альтернатива «папкам по типу файлов» (`components/`, `hooks/`, `utils/`).
>
> Сайт: [feature-sliced.design](https://feature-sliced.design)

## Проблема которую FSD решает

Плоская структура `src/components/`, `src/hooks/`, `src/utils/` работает на 10 компонентах. На 100 — превращается в кашу:

- Любой компонент может импортировать любой другой → циклические зависимости, паутина
- Невозможно сказать «эта фича изолирована» — её зависимости размазаны по всему проекту
- Удалить фичу = долго искать что куда тянет
- Новичок в команде не знает с чего начать читать

FSD отвечает: **группируем код по бизнес-смыслу, ограничиваем что откуда можно импортировать**. Структура становится навигационной картой проекта.

## Слои

Шесть слоёв, сверху вниз:

| Слой         | Что хранит                                           | Пример                                        |
| ------------ | ---------------------------------------------------- | --------------------------------------------- |
| **app**      | Инициализация приложения, провайдеры, store, стили   | `app/store.ts`, `app/providers/StoreProvider` |
| **pages**    | Экраны, соответствующие роутам                       | `pages/home`, `pages/settings`                |
| **widgets**  | Самостоятельные UI-блоки, композиция фич и сущностей | `widgets/header`, `widgets/todo-board`        |
| **features** | Пользовательские взаимодействия с бизнес-смыслом     | `features/add-todo`, `features/filter-todos`  |
| **entities** | Бизнес-сущности предметной области                   | `entities/todo`, `entities/user`              |
| **shared**   | Переиспользуемое без бизнес-смысла                   | `shared/ui/Button`, `shared/lib/formatDate`   |

**Главное правило**: слой может импортировать **только из слоёв ниже**. `pages/` может из `widgets/`, `features/`, `entities/`, `shared/`. Но `entities/` **не может** из `features/`. Это и делает архитектуру читаемой — направление зависимостей одно, никаких циклов.

```
app  ────────► может импортировать ────►  pages
                                      └──►  widgets
                                      └──►  features
                                      └──►  entities
                                      └──►  shared

shared  ────────► НЕ импортирует ничего из верхних слоёв
```

### Как различать widget / feature / entity

Это самая частая точка путаницы. Тест:

- **Entity** отвечает на «**что это** в предметной области?». Имеет имя в речи бизнеса (todo, user, order). Знает свою форму данных и как себя отобразить. Не знает про действия других сущностей.
- **Feature** отвечает на «**что пользователь хочет сделать?**». Глагол: добавить-todo, отфильтровать-список, залогиниться. Использует одну или несколько сущностей.
- **Widget** отвечает на «**какой это блок UI?**». Существительное, но **не** доменное: header, sidebar, todo-board. Композиция: соединяет фичи и сущности в готовый кусок интерфейса.

Пример: «корзина в интернет-магазине»

- `entities/product` — что такое товар, как его показать (карточка)
- `entities/cart` — что такое корзина, какие у неё методы (.add, .remove)
- `features/add-to-cart` — кнопка «купить» на карточке + логика добавления
- `features/cart-checkout` — формы оформления заказа
- `widgets/header` — шапка с иконкой корзины и счётчиком
- `pages/product` — страница товара, собирающая `entities/product` + `features/add-to-cart` + всякие виджеты

## Слайсы

Внутри каждого слоя — **слайсы** (slices). Слайс = доменная единица. В `entities/` каждая сущность — отдельный слайс. В `features/` каждое действие — отдельный слайс.

```
src/
  entities/
    todo/         ← слайс
    user/         ← слайс
  features/
    add-todo/     ← слайс
    filter-todos/ ← слайс
```

**Слайсы одного слоя не общаются между собой напрямую.** `features/add-todo` не импортирует `features/filter-todos`. Если им нужно связаться — это делает слой выше (widget или page).

Это правило выглядит странно пока с ним не поработаешь. Смысл: слайсы должны быть **независимыми единицами**. Если `add-todo` начинает дёргать `filter-todos`, они становятся одной фичей. Тогда либо это правда одна фича (и нужно слить), либо нужен посредник этажом выше.

Исключение — `shared/` и `entities/`: к ним могут обращаться все, кому ниже разрешено. Это правило про слайсы внутри `features/`, `widgets/`, `pages/`.

## Сегменты

Внутри слайса — **сегменты** по технической роли:

```
entities/todo/
  ui/        ← React-компоненты этой сущности
  model/     ← state, types, селекторы, slice
  api/       ← запросы к серверу для этой сущности
  lib/       ← утилиты сущности
  config/    ← константы
  index.ts   ← public API (см. ниже)
```

Не все сегменты обязательны. Простой слайс может иметь только `ui/` + `index.ts`. Сегмент появляется когда есть что в него класть.

## Public API через `index.ts`

**Главный технический паттерн FSD.** Каждый слайс экспортирует наружу только то что лежит в его `index.ts`. Всё остальное — внутреннее устройство, недоступное извне.

```ts
// entities/todo/index.ts
export { TodoItem } from './ui/TodoItem/TodoItem';
export type { Todo } from './model/types';
// НЕ экспортируем: внутренние компоненты, хелперы, типы только для внутренних нужд
```

Правильный импорт:

```ts
import { TodoItem, type Todo } from '@/entities/todo';
```

Неправильный (нарушает изоляцию):

```ts
import { TodoItem } from '@/entities/todo/ui/TodoItem/TodoItem';
import type { Todo } from '@/entities/todo/model/types';
```

Зачем:

- **Переименовать внутренний файл — не сломать остальной проект.** Только `index.ts` это знает.
- **Видно границу слайса.** Что снаружи — public контракт. Что внутри — твоё дело.
- **Меньше связности.** Внешний код не лезет в кишки.

Линтер навязывает это правило — без него легко случайно написать длинный путь и забыть.

## Применимо к нашему проекту

Сейчас:

```
src/
  components/
    ui/{Button,Checkbox,IconButton}/
    TodoInput/
    TodoItem/
    TodoList/
    TodoFilter/
  types/todo.ts
  App.tsx
  main.tsx
```

После FSD:

```
src/
  app/
    providers/         ← когда появятся (Redux Provider, Theme, и т.д.)
    main.tsx           ← бывший src/main.tsx (точка входа)
    index.css          ← бывший src/index.css (глобальные стили)
  pages/
    home/
      ui/HomePage.tsx  ← бывший App.tsx
      index.ts
  widgets/
    todo-list/
      ui/TodoList/     ← бывший components/TodoList
      index.ts
  features/
    add-todo/
      ui/AddTodoForm/  ← бывший components/AddTodoForm
      index.ts
    filter-todos/
      ui/TodoFilter/   ← бывший components/TodoFilter
      model/
        types.ts       ← FilterStatus (из старого src/types/todo.ts)
      index.ts
  entities/
    todo/
      ui/TodoItem/     ← бывший components/TodoItem
      model/
        types.ts       ← Todo (из старого src/types/todo.ts)
      index.ts
  shared/
    ui/
      Button/          ← бывший components/ui/Button
      Checkbox/        ← бывший components/ui/Checkbox
      Input/           ← бывший components/ui/Input
      index.ts         ← root barrel UI kit'а
```

Ключевые решения по нашему коду:

- **`TodoItem` → entity.** Это представление сущности `Todo`. Знает как отобразить todo, не знает откуда тот взялся и что с ним делать.
- **`AddTodoForm` → feature `add-todo`.** Действие пользователя — добавление новой todo. Глагол.
- **`TodoFilter` → feature `filter-todos`.** Действие — переключение фильтра.
- **`TodoList` → widget `todo-list`.** Композиция: рендерит много `TodoItem`, принимает обработчики. Для чистого переноса оставили имя `TodoList` (без переименования в `TodoBoard`).
- **`App.tsx` → page `home`.** Вся логика приложения была в `App`. По FSD page просто собирает виджеты и фичи; наш `home` собирает `todo-list` + `add-todo` + `filter-todos`. Компонент переименован `App` → `HomePage`.
- **`Todo` → `entities/todo/model/types.ts`**, **`FilterStatus` → `features/filter-todos/model/types.ts`.** Тип `Todo` принадлежит сущности, `FilterStatus` — фиче фильтрации, поэтому они разъехались по разным слоям. Старый `src/types/todo.ts` удалён.

## Типичные ошибки

**1. Класть доменные типы в `shared/`.**

> `shared/types/todo.ts` ← ❌ `Todo` это сущность, ей место в `entities/todo/model/`. В `shared/` идёт только то у чего нет бизнес-смысла.

**2. Импортировать `feature` в `entity`.**

> ❌ `entities/todo/ui/TodoItem.tsx` импортирует `features/delete-todo`. Это переворачивает направление зависимостей и делает entity несамостоятельной. Правильно: TodoItem принимает обработчики через props, widget/page их пробрасывает.

**3. Слияние слайсов одного слоя.**

> ❌ `features/add-todo` импортирует из `features/filter-todos`. Если им правда нужно общаться — посредник этажом выше. Если они логически одно — слить в одну фичу.

**4. Большой `shared/ui/`.**

> Каждый компонент кидаем туда — потому что «вдруг переиспользуем». В итоге `shared/ui/` распухает, ничего там не находится. Правило: в `shared/` попадает то что **уже** переиспользуется в 2+ местах и не имеет бизнес-смысла. Заранее — не нужно.

**5. Импорт мимо `index.ts`.**

> `import { TodoItem } from '@/entities/todo/ui/TodoItem/TodoItem'` — обходит публичный API. Линтер должен это ловить.

**6. Запихнуть всё в `pages/`.**

> Когда страница знает слишком много, она перестаёт быть «сборкой» и становится монолитом. Если в `pages/home/ui/HomePage.tsx` 300 строк JSX — пора выделять виджеты.

## Что НЕ делает FSD

- **Не диктует библиотеки.** Можно с Redux, Zustand, MobX, без state-менеджера вообще. С React Query, без него. FSD про границы модулей, не про инструменты.
- **Не решает за тебя где провести границу feature/widget.** Это всегда subjective. Команда вырабатывает соглашения по ходу.
- **Не пишет тесты, не выбирает CSS-решение, не настраивает CI.** Архитектура папок и импортов, не больше.

## Стоит ли это для нашего проекта

Прагматично — для 5 компонентов и одной странички FSD оверкилл. То что мы делаем сейчас — **учебный** заход:

- Сразу поработать руками с настоящей промышленной архитектурой
- Получить ощущение «как должно быть» когда столкнёшься на работе
- Подготовить плацдарм для следующих глав (Redux, потом ещё фичи) чтобы каждый новый кусок сразу ложился в правильное место

Если этот проект был бы продакшеновым прототипом на неделю — оставили бы плоскую `components/` структуру.

## Что мы сделаем в этой главе

1. Поставим линтер с правилами FSD (`eslint-plugin-boundaries` или аналог)
2. Создадим папки слоёв (`app/`, `pages/`, `widgets/`, `features/`, `entities/`, `shared/`)
3. Перенесём существующие компоненты по слоям — снизу вверх (`shared` → `entities` → `features` → `widgets` → `pages`), одним коммитом на слой
4. Каждому слайсу добавим `index.ts` с public API
5. Обновим импорты во всех файлах (TS поможет, но проверим вручную)
6. Прогон Storybook + сборки — всё должно работать
7. Прогон по `wiki/` — обновим пути в примерах кода если ссылаются на старые места

После этого проект готов принять Redux в правильную форму, а не «куда придётся».
